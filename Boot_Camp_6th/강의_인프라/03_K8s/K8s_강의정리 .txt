1. 개념
	- 오픈 소스 시스템
	- Docker같은 컨테이너를 관리 (생성/사용/종료/재포) 하는 시스템의 표준 (오케스트레이션 역할)
	
	https://kubernetes.io/

-------------------------------------------------------------------------------------------------------------------	
2. 특징 

	- 어플리케이션 부하에 따른 자동 배포기능
	
	- 쉬운 scaling과 Load Balancing ( 요청 분배 )	
	# 요청이 늘어날때 pod를 늘려 요청을 분배하게 용이하다.
	# 기본적으론 라운드로빈 방식을 따른다.
	# 라운드로빈: 
	라운드 로빈(Round Robin)은 네트워크 인그레스(Ingress) 또는 서비스(Service) 객체로 들어오는 클라이언트의 요청(Request)을 연결된 백엔드 엔드포인트(Endpoint, 즉 여러 개의 Pod)에 순차적으로 하나씩 할당하는 정적 부하 분산(Load Balancing) 알고리즘입니다.
	# 특정 url을 특정 노드로 지정하는 방식도 가능하다.
	
	- 자동으로 네트워크 구성
	
	- 문제 발생 시 컨테이너 자동 재시작 및 재배치	
	# 노드에서 pod 재시작은 K8s 정책을 따른다
	# 워커 노드의 pod 수용가능 여부를 파악해서 수용가능한 노드에서 재시작
	# ==> pod가 죽은 노드와 재시작하는 노드가 다를 수가 있다.
		  이때 다른 노드에서 재시작한 pod는 기존의 노드에 volume 했던 데이터가 유실될 수 있다.
	
	- 필요시 이전 버전으로 롤백. ( 바로이전, 특정버전 롤백 가능 )
	# 마스터노드의 etcd에 노드에서 발생하는 정보가 저장된다
	# ==> 이전 버전으로 롤백 해도 히스토리는 유지된다
	
	- 표준이기 때문에 어떤 클라우드 공급자와도 연동이 가능 ( AWS, Azure(MS), GCP(google) )

3. K8s Architecture
	https://kubernetes.io/ko/docs/concepts/architecture/
	
	K8s 클러스터
	-----------------------------------------------------------------
	Control Plane			---------------->	Data plane
	(Master node: 노트북1)						-----------------
												Worker Node(노트북2)	ex. App Pod
												...
												Worker Node(노트북 n)	ex. DB Pod
	-----------------------------------------------------------------												
												
	Control Plane	: 관리자 역할 ( 마스터노드 )
	Worker Ndoe		: 실제 컨테이너를 실행하는 서버

-------------------------------------------------------------------------------------------------------------------
4. 클러스터 
	
	1) 개념
		- 여러대의 컴퓨터(노드)를 하나의 컴퓨터처럼 동작하도록 구축한 시스템
	
	2) 필요성
		가. 서버 1대로 운영 시
			- 서비스 장애 발생시 바로 서비스 종료.
			- 트래픽 증가 시 확장 어려움
			
		나. 클러스터 운영 시
			- 여러 노트데 분산 배치 가능 
			- 장애 발생 시 다른 노드로 재배치
			- 트래픽 증가 시 요청분배 가능
			
	3) 노드(Node)
		
		가. 개념: 클러스터를 구성하는 컴퓨터 의미 
		
		나. 종류 
			
			- Control Plane( Master node )
				: 클러스터 전체를 관리하는 역할
				: 구성요소 4가지
					> kube-api-server		: Worker node의 kubelet과 연동
					> scheduler				: Pod를 어느 노드에 배포할 지 결정
					> controller-manager	: Worker node에 있는 pod 복구 담당 ( pod 갯수 등 참고 )
					> etcd					: 클러스터의 상태 정보 저장소
					
			- Data Plane( Worker node)
				: 실제 기능을 가진 Pod를 실행하는 역할
				: 구성요소 3가지
					> kubelet		: Master node와 통신 담당
									  Pod 생성 및 컨테이너 생명주기 보장									  
					> CRI(Container Runtime Interface)	: Pod(컨테이너)를 실행하는 런타임.
														  ex. containerd, CRI-O
					> kube-proxy	: Node와 Pod등에서 사용하는 네트워크 통신 담당

-------------------------------------------------------------------------------------------------------------------
5. Control Plane ( Master node ) 

	1) 개념
		: 클러스터 전체를 관리하는 역할의 서버 
		
	2) 구성요소
		가. API Server		
			- K8s 외부에 노출하는 구성요소, 모든 작업의 진입점(Entry point) 역할
			- 사용자가 요청하는 명령어(kubectl)를 가장 먼저 받아서 처리한다.
		
		나. Scheduler				
			- Pod를 어떤 노드에 배치할 지를 결정
			- 노드의  CPU / Memory 자원 사용량 및 규칙 ( ex. 특정노드에서만 배포)을 고려해서 적합한 노드를 선택
		
		다. Controller Manager
			- 클러스터를 원하는 상태(desired state)로 유지하기 위해서 사용하는 구성요소
			  ==> 문제가 있어서 종료된 Pod를 다시 복구한다
			- desired state를 맞추기 위한 다양한 controller들이 동작한다 
				> Node controller	: 노드 상태 관리
				> Job controller	: 일회성 작업을 나타내는 잡(Job)를 감시하고, 파드를 생성한다.
				...
			
		라. Etcd
			- 클러스터의 상태 정보 저장소
			- key / value 형식
			- 대표적으로 pod, service, replicaset, configmap 등 리소스 정보를 저장 / 관리
					
-------------------------------------------------------------------------------------------------------------------
6. Worker node
	
	1) 개념
		- 실제 컨테이를 포함하는 Pod가 실행되는 곳
		
		
	2) 구성요소 
		
		가. kubelet 
			- Master node의 API Server와 통신 담당
			- 주로 Worker node의 상태 정보(pod 등 리소스 상태)를 master node에게 전달
			
		나. kube-proxy
			- Node와 Pod등에서 사용하는 네트워크 통신 담당

		다. CRI( containerd )
			- Pod(컨테이너)를 실행하는 런타임.
			- CRI(Container Runtime Interface)이고 컨테이너를 실행하는 스펙을 정의한 개념
			  ( 자바의 Interface와 비슷 )
			- 실제 구현한 구현물 :  containerd, CRI-O 등
			- 용도: 컨테이너를 실행하는 러타임 환경을 제공
					==> 컨테이너를 생성하기 위한 이미지 다운로드 
						컨테이너 생성/중지/삭제 등

3장 kubectl
/////////////////////////////////////////
1. 개요
	
	https://kubernetes.io/docs/reference/kubectl/
	- K8s 클러스터를 관리(제어)하는 명령어. (CLI 기반)
	- K8s 설치하면 자동으로 설치됨
	- Master Noded의 API Server와 통신
	
				kubectl get nodes
				(REST API 형태로 요청) 
		사용자 --------------------> API Server ----> 처리
		
2. 문법
	
	kubectl [command] [TYPE] [NAME] [flags]
	- command: 리소스(pod, service, ... )에 대해서 수행할 동작
			 ex. get		: 리소스 조회
				 delete		: 리소스 삭제
				 describe	: 상세 정보 조회
				 apply		: 리소스 생성/수정
				 logs		: 로그 확인
				 exec		: 컨테이너 접속/명령어 실행
				 rollout	: 배포관리 ( 롤백 포함 )	# rolling update가 기본이다
				 config 	: 클러스터 접속관리 ( 로컬 / 클라우드 )

	- TYPE: 대상이 되는 리소스 종류 ( 대소문자 구별안함, 단수/복수/약어 모두 가능 )
	# kubectl api-resources		# K8s이 지원하는 resource 목록확인
	
		ex. pod, pods, po 모두 가능
	
	- NAME: 리소스명 ( 대소문자 구별한다, NAME을 지정하지 않으면 모든 리소스 의미 )
		ex. kubectl get pods			# 모든 pod를 조회
			kubectl get pods my-pod		# 특정 pod(NAME)을 조회
			
	- flags: 옵션
		ex. -f		: 파일 지정.
			--all	: 모든것 의미 ex. kubectl delete all --all		# 모든 리소스의 모든 내용을 삭제
			-it		: 인터렉티브 접속.
			...

4장 kubeconfig 개요
/////////////////////////////////////////

	1) 개념
		- kubectl 클러스터에 접속하기 위해서 사용하는 설정파일
		- 윈도우: C:\Users\qja03\.kube\config 에 저장되어 있음. ( 나중에 AWS 클러스터 추가하면 이 파일에 추가됨 ) 
		- 리눅스: .kube/config
		
	2) 구성요소 3가지 
	
		가. cluster
			- 접속할 K8s의  클러스터 정보가 저장됨.
				ex. API Server 주소, 클러스터 이름
			
		나. contexts
			- cluster와 user 정보를 연결한 설정
			
		다. user
			- 접속할 사용자 정보.
				ex. 사용자명, 인증정보 등
				
	3) 특징
		- 여러 클러스터 정보 저장이 가능
		- 여러 사용자 정보 저장이 가능
		
		https://kubernetes.io/docs/reference/kubectl/generated/kubectl_config/
		
		kubectl - kubectl controls the Kubernetes cluster manager
		kubectl config current-context - Display the current-context
		kubectl config delete-cluster - Delete the specified cluster from the kubeconfig
		kubectl config delete-context - Delete the specified context from the kubeconfig
		kubectl config delete-user - Delete the specified user from the kubeconfig
		kubectl config get-clusters - Display clusters defined in the kubeconfig
		kubectl config get-contexts - Describe one or many contexts
		kubectl config get-users - Display users defined in the kubeconfig
		kubectl config rename-context - Rename a context from the kubeconfig file
		kubectl config set - Set an individual value in a kubeconfig file
		kubectl config set-cluster - Set a cluster entry in kubeconfig
		kubectl config set-context - Set a context entry in kubeconfig
		kubectl config set-credentials - Set a user entry in kubeconfig
		kubectl config unset - Unset an individual value in a kubeconfig file
		kubectl config use-context - Set the current-context in a kubeconfig file
		kubectl config view - Display merged kubeconfig settings or a specified kubeconfig file
		
		ex. 
			# 1. config 내용 조회
			config 파일 내용 조회
			kubectl config view			# 민감 정보 미출력
			kubectl config view --raw	# 민간 정보 출력
			
			# 2. 현재 사용중이 컨텍스트

5장 K8s의 Configuration 설정 방법
/////////////////////////////////////////

	1) 개념
		- K8s에 리소스 (Pod, Service, ...)등을 어떻게 생성할 것인지를 정의하고 관리하는 방식관련 내용임.
	
	2) 방법 2가지 
		
		가. 명령형 구성 방법 ( Imperative Configuration ) 
			- 시스템에 직접 명령어 입력하는 방식
			ex. docker run -p 8080:80 nginx
				kubectl run nginx
				
			장점:
				즉각적으로 실행가능
				직관적임.
				
			단점:
				문서화 되지 않아 이력관리가 안됨.
				재현성 떨어짐				
		
		나. 선언형 구성 방법 ( Declarative Configuration )]
			- yaml 파일에 클러스터에 구축하고자 하는 원하는 상태(desired state)를 코드화 하는 방법
			
			- 장점:
				문서화 되어 있어서 이력관리가 가능하다
				재현성 향상
				대규모 운영에 유리
				
	3)  K8s의 YAML( Yet Another Markup Language, manifest 파일이라고도 부른다 )
		
		가. 개념
			- K8s의 클러스터가 원하는 상태( Desired state )를 갖도록 설정하는 파일(***********)
		
		나. 공통 구조
			
			apiVersion:	v1 | apps/v1	# API 버전, 확인방법: kubectl api-resources, kubectl api-versions
			kind: Pod | Deployment		# 생성하려는 리소스  종류 ex. Pod, Service, Deployment, ... 
										  대소문자 구별됨.
			metadata:					# Kind의 추가 설정정보.
										  ex. 이름, 라벨, 네임스페이스			
			spec:						# 리소스마다 다르다. 개별적인 리소스마다 정리 필요.
			
		다.	YAML 작성 가이드
			
			각 리소스마다 yaml 내용은 https://kubernetes.io/docs/home/ 검색해서 복사 / 붙여넣기 해서 사용한다.
			
			kubectl explain pod					# pod에 대한 소개 및 필드(field) 소개 
			kubectl explain pod.spec			# pod의 spec 소개
			kubectl explain.pod.spec.containers	# pod의 spec에서 containers 항목소개 
					
		라. kubectl과 yaml 처리 
		
			- 동작반식 
							pod.yaml --> JSON
				kubectl ---------------------------> API Server
			 (pod.yaml)

6장 K8s의 주요 객체 1 - Pod
/////////////////////////////////////////
	
1. 개념 
	- K8s 에서 관리( 생성/수정/삭제 )하는 최소 단위임 ( docker에서는 컨테이너가 최소 단위였음 )
	- Pod 안에서 하나 이상의 컨테이너를 포함함( 일반적으로 하나의 컨테이너를 가짐 ) 
	  # 하나의 Pod에 두개 이상의 컨테이너가있는 패턴 : 사이드카( Side car ) 패턴
	  
		https://kubernetes.io/docs/concepts/workloads/pods/

2. 특징
	1) Pod 안에 한 이상의 컨테이너를 포함함.
	2) Pod 안에 있는 컨테이너들이 네트워크와 볼륨을 공유할 수 있음 (****) 
	
	--------------------------
	Pod
	
		--------------
		container1
		--------------
		
		--------------
		container2
		--------------
		
		shared Network
		shared Volume
	--------------------------
	
	3) Pod는 일시적 ( Ephemeral ) 객체이다 ( 영구적인 객체가 아니다 )
		언제든지 제거될 수 있고, 새로운 Pod가 생성될 수 있다.
		ex. Node 장애 
			Pod 삭제 
			Deployment 업데이트
			Scale Out/In ( 트래픽에 따른 Pod 갯수 증가/감소 )
			
		==> Pod에서 처리한 데이터는 기본적으론 유지 불가( 영속성을 위해서 Volume 사용함 )
		  
	4) Pod는 직접 생성하기 보다는 다른 리소스를 이용해서 만드는것이 일반적이다.
		-> 더 많은 기능을 포함할 수 있기 때문
		ex. Deployment, StatefulSet, Job, CronJob
		
	5) Pod는 lifecycle 가짐.
		https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/
		
		pending --> runninng --> succeeded / failed
	
		pending		: Pod가 생성되었으나 아직 실행되지 않음
		running		: 하나 이상의 컨테이너가 실행중
		succeeded	: 하나 이상의 컨테이너가 모두 정상종료
		failed		: 하나 이상의 컨테이너가 비정상종료
		Unknown		: 노드와 통신불가로 인해 상태확인 불가
	
		확인방법: kubectl get pods
		
	6) RestartPolicy 정책
		- Pod가 제거된 후 재시작과 관련된 정책
		
		가. Always		: 컨테이너가 종료되면 항상 재시작된다.
		나. OnFailure	: 실패했을때만 재시작	# non-zero exit status: 0코드(정상종료코드)가 아닌 상태가 존재할때
		다. Never		: 재시작 하지 않음
		
	7) Image관련 정책 ( ImagePullPolicy )
	
		https://kubernetes.io/docs/concepts/containers/images/#image-pull-policy
		
		- Pod가 실행될때, 컨테이너에서 이미지를 언제, 어떤 방식으로 hub에서 가져올지 결정하는 정책
		- 정책 3가지 
			가. Always		: 매번 hub에서 가져온다
							  ( 로컬에 cached된 이미지가 있다면 로컬 이미지를, 없다면 허브에서 가져온다 )
				
			나. IfNotPresent: Node(local)에 이미지가 없을때만 다운로드 ( 가장 많이 사용 )
				
			라. Never		: 항상 로컬에 있는 이미지 사용
			
		- ImagePullPolicy를 생략했을 경우 기본값
			가. tag가 :latest인 경우
				- 기본적으로 Always로 동작됨
		
			나. tag가 특정 버전인 경우 ( :latest가 아닌 경우 )
				- 기본적으로 IfNotPresent로 동작한다
		
		
		- ImagePullBackOff
		https://kubernetes.io/docs/concepts/containers/images/#imagepullbackoff
			==> K8s가 이미지를 가져오지 못해 container를 생성하지 못하는 경우.
			
			원인 : 이미지 이름 오타, tag 오타, 로컬 이미지 없이 Never 지정한 경우
			
			==> kubectl describe pod <파드명>  확인 가능
	
	8) label 사용
	https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/
	
	- 개념: K8s 리소스( Pod, Service, Deployment 등 )에 설정하는 key-value 값.
	- 용도: 다른 리소스에서 접근할 때 label(ex. Pod) + selector(ex. Service) 사용함.

				: 컨테이너가 계속 죽고 살아나는 동작을 반복

	5) Pod 내의 컨테이너에서 실행되는 어플리케이션( ex. SpringBoot) 로그 출력
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_logs/
	
		- 개념
		  : 컨테이너에서 실행되는 어플리케이션( ex. SpringBoot)의 정상로그(표준출력) 와 오류로그(표준에러)를 출력하는 명령어
		
		- 문법: kubectl logs [-f] [-p] (POD | TYPE/NAME) [-c CONTAINER]
		
			-f, --follow	: 인텔리제이 로그처럼 실시간으로 로그 출력 가능.
			-p, --previous	: If true, print the logs for the previous instance of the container in a pod if it exists.
			-c  CONTAINER	: 컨테이너명 지정			
			--tail n		: 마지막 로그중 n개 만큼 출력
			--timestamps	: 시간출력
			-p, --previous	: 만약 파드에 이전에 존재 했던 컨테이너가 있다면, 로그를 프린트해라
							  ex. CrashLoopBackOff 발생시 필수로 봐야된다
			-l, --selector string	: 필터링
			--since duration		: 지정된 시간 이후 로그만 출력 ( 단위 : 2s, 2m, 2h )
			
		ex.
			kubectl logs nginx-pod
			kubectl logs nginx-pod --tail 10
			kubectl logs nginx-pod --since=1m
			kubectl logs nginx-pod -c nginx-container

	8) Label CRUD
		
		- 개념: label을 추가/수정/삭제/조회 하는 명령어
		- 문법: 
			kubectl label [--overwrite] (-f FILENAME | TYPE NAME) KEY_1=VAL_1 ... KEY_N=VAL_N [--resource-version=version]

		- 옵션
			--overwrite		: 기존 라벨 덮어쓰기 ( 수정 ) 
			--all			: 모든 리소스 선택
							  ex. kubectl label pods --all key=value	# 모든 pod에 라벨 지정
			-f FILENAME		: 지정된 파일의 리소스에 라벨 추가.
			--list			: 라벨 출력
			key-			: 라벨 삭제		ex. kubectl label pods pod4 app-  , env-

			kubectl label --overwrite pods nginx-container status=unhealthy		# 라벨수정
			kubectl label pods nginx-container bar-					# 라벨 삭제

			kubectl get pods -L app,env					# 지정된 라벨을 column 으로 출력

7장 Pod의 리소스 자원 (CPU/Memory) 관리
/////////////////////////////////////////
https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#requests-and-limits

1. 개념	: 여러 Pod들이 Node의 CPU와 Memory를 공유해서 사용한다. 
		  특정 Pod가 과도하게 자원을 점유하면 다른 Pod데 문제가 발생
		  ==> CPU, Memory 사용량에 대한 제한을 설정한다
	
	---------------------------
	Node ( PC )
	
	-----
	pod( SpringBoot )	- 희망 자원 : 최소한의 필요자원 지정 ( ex. CPU:1, Memory: 1Gi )
	-----				- 제한 자원 : 최대 사용할 수 있는 자원지정 ( ex. CPU:2, Memory: 3Gi )	  
									  CPU를 초과사용으로 사용제한 ( Throttling )
	-----							  Memory 초과사용으로 종료 ( OOMKill )		
	pod( MySql, Redis )
	-----
	
	CPU 자원 (ex. I7 12core)
	Memory 자원 (32g)
	---------------------------

2. 설정 방법

	spec:
	  containers:
		resources:
		  requests:		# 희망자원
			memory: "64Mi"
			cpu: "250m"
		  limits:		# 제한자원
			memory: "128Mi"
			cpu: "500m"
			
3. 단위

	가. CPU 단위 ( MilliCPU )
		- 1000m = 1 CPU == 1 Core
		ex. 100m = 0.1 CPU
			250m = 0.25 CPU
			500m = 0.5 CPU
			1000m = 1 CPU
			
	나. Memory 단위
	
		- ki : kibi byte 	( 1ki = 1024 byte )
		- mi : mibi byte	( 1Mi = 1024^2 byte )
		- Gi : Gibi byte	( 1Gi = 1024^3 byte )
		
		ex. 1Gi = 1024MB
			128Mi = 128MB
			
4. requests
	- 개념 : 최소 보장 자원
			 ( 최소한 이 정도의 CPU와 Memory가 필요하다)
			 
	- 용도 : scheduler가 Pod를 어느 node에 올릴지 결정하는 기준이 된다.
			 중요한 것은 실행했을 때 필요한 자원이 기준이 아님. 	==>  실제 필요한 자원의 기준이 아닌 개발자가 지정한 기준이다
			 requests에 부합되지 않는 Node에는 배치되지 않는다.
			  
5. limits
	- 개념: 최대 사용 자원
	- 용도: 리소스(Pod) 보호.
			특정 Pod가 자원을 독접하지 못하도록 제한함.
			
	- 동작: 
		CPU가 초과되면 Throttling 발생 ( 최대 상한선에서 사용되도록 강제 )
		Memory가 초과 되면 강제종료 ( OOMKill 라고 부름 )
		
	
	# 실습1. CPU 실습
		
		1) yaml 작성( pod9.yaml )
			
			apiVersion: v1
			kind: Pod
			metadata:
			  name: stress-cpu
			spec:
			  restartPolicy: Never
			  containers:
				- name: stress
				  image: polinux/stress
				  args: ["stress", "--cpu", "1", "--timeout", "120s", "--verbose"]
				  # args: ["stress", "--vm", "1", "--vm-bytes", "300M", "--timeout", "120s", "--verbose"]
				  resources:
					requests:
					  cpu: "200m"
					  memory: "64Mi"
					limits:
					  cpu: "500m"
					  memory: "128Mi"
					  
		args: ["stress", "--cpu", "1", "--timeout", "120s", "--verbose"]
		==> CPU 1개를 이용해서 엄청낙 많은 연산작업을 수행함.
			120초 이후에는 연산작업을 끝냄.
		
		2) Pod 생성
			> kubectl apply -f pod9.yaml
			
		3) Pod 자원 확인 			
			> kubectl top pods
			NAME         CPU(cores)   MEMORY(bytes)   
			stress-cpu   465m         0Mi  				# 최대 CPU 점유율이 500Mi를 넘지 않는다
			
	
	# 실습2. Memory 실습
		
		1) yaml 작성( pod9.yaml )
			
			apiVersion: v1
			kind: Pod
			metadata:
			  name: stress-cpu
			spec:
			  restartPolicy: Never
			  containers:
				- name: stress
				  image: polinux/stress
				  # args: ["stress", "--cpu", "1", "--timeout", "120s", "--verbose"]
				  args: ["stress", "--vm", "1", "--vm-bytes", "300M", "--timeout", "120s", "--verbose"]
				  resources:
					requests:
					  cpu: "200m"
					  memory: "64Mi"
					limits:
					  cpu: "500m"
					  memory: "128Mi"
					  
		args: ["stress", "--vm", "1", "--vm-bytes", "300M", "--timeout", "120s", "--verbose"]
		==> Memory가 300M 필요하도록 스트레스 부하
			120초 이후에는 작업을 끝냄.
			이때 limits:memory: "128Mi" 이므로 OOMKill 된다
		
		2) Pod 생성 
			> kubectl apply -f pod9.yaml
			
		3) Pod 상태 확인		
			> kubectl get pods           
			NAME         READY   STATUS      RESTARTS   AGE
			stress-cpu   0/1     OOMKilled   0          13s

6장 K8s 주요객체2 - Namespace
/////////////////////////////////////////
https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/
https://kubernetes.io/docs/reference/kubernetes-api/core/namespace-v1/

1. 개념
	- 하나의 K8s의 클러스터를 논리적으로 어러개 분리해서 관리하는 기능임
	
2. 목적
	- K8s의 클러스터에 있는 여러 리솟스들을 용이하게 관리하기 위함
	( 자바의 패키지 기능과 비슷 )

3. 특징 
	- 하나의 리소스는 하나의 Namespace에 속함
	- 같은 Namespace 안에서는 리소스 이름이 유일, 
	  다른 Namespace 간에는 리소스 이름 중복가능
	- default Namespace가 제공된다 
	- 모든 리소스가 Namespace를 사용하는 것은 아니다.
		
		# kubectl api-resources의 NAMESPACED로 확인 가능
		
		> Namespace 적용가능한 리소스
		  : Pod, Service, Deployment, ReplicaSet, ConfigMap, Secret, PVC(PersistentVolumeClaim), StatefulSet, Job, CronJob, Ingress
		
		> Namespace 적용이 불가능한 리소스(클러스터 단위)
		  : Node, Namespace, PersistentVolume
		  
	- Namespace를 삭제하면 그 안에 있는 리소스(pod, service 등)들도 같이 삭제가 된다.(**)
	- 리소스를 조회할 때, 반드시 Namespace 명을 지정해야 된다.
	  ex. kubectl get pods						# default Namespace에서 찾음
		  kubectl get pods -n 네임스페이스명 	# 지정된 Namespace에서 찾음
												# -n, --namespace 는 상위 옵션이다
												
	- 기본으로 제공되는 Namespace
	  : kube-node-lease, kube-public, kube-system
	  
4. Namespace 관련 주요 명령어
	
	1) Namespace 생성
		가. 명령형 ( Imperative )
		https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/kubectl_create_namespace/
			
			- 문법: kubectl create namespace NAME [--dry-run=server|client|none]
				ex. kubectl create namespace my-namespace --dry-run=client -o yaml
				# --dry-run=client 사용하는 이유
				# 오직 사용자의 컴퓨터(kubectl 도구) 내부에서 명령어의 문법이 올바른지, 리소스 객체가 문법에 맞게 만들어지는 검증하기위해

		나. 선언형 ( Declarative: yaml + kubectl apply )
		https://kubernetes.io/docs/tasks/administer-cluster/namespaces/
			
			# namespace.yaml
				apiVersion: v1
				kind: Namespace
				metadata:
				  name: <insert-namespace-name-here>
			  
			kubectl apply -f namespace.yaml
			
	2) Namespace 보기 
		
		kubectl get namespace
		kubectl get ns
		
	3) Namespace 자세히 보기
		
		kubectl describe namespace
		kubectl describe namespace my-name
		
	4) Namespace 삭제 
	
		kubectl delete namespace my-namespace
		kubectl delete ns my-namespace
		
	5) Namespace 별 리소스 조회
		kubectl get pods 					# default 네임스페이스에서 찾음
		kubectl get -n my-namespace 		# default 네임스페이스에서 찾음
		
		kubectl get pods -A					# 모든 네임스페이스에서 찾음
		kubectl get pods --all-namespace	# 모든 네임스페이스에서 찾음

6장 K8s 주요객체3 - ReplicaSet
/////////////////////////////////////////			
https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/
https://kubernetes.io/docs/reference/kubernetes-api/apps/replica-set-v1/

1. 개념
	- 지정한 갯수만큼 Pod를 생성해주는 리소스
	  만약에 하나의 Pod가 장애로 인해 종료되면, current state와 desired state 비교해서 
	  desire state 상태로 만듬.
	- ReplicaSet 삭제하면 관련된 Pod들도 같이 삭제된다

2. 목적 
	- Pod 갯수 유지 ( desired state 유지 )
	- 고가용성 보장
	
	# sample.yaml 
		apiVersion: apps/v1			# API Version. kubectl api-resources 확인 가능
		kind: ReplicaSet
		metadata:
		  name: frontend			# ReplicaSet 이름
		  labels:					# Label 지정
			app: guestbook
			tier: frontend		
		spec:
		  # modify replicas according to your case
		  replicas: 3				# Pod 개수 지정, Desired stste
		  selector:					# 접근하고자 하는 리소스를 찾을 떄 사용하는 속성
			matchLabels:
			  tier: frontend		# selector가 match 하려는 라벨(*)
			  
		  template:					# ReplicaSet이 만들어야 되는 Pod 정보를 지정하는 영역
			metadata:
			  labels:
				tier: frontend		# selector가 접근할 리소스, matchLabels와 같은 라벨이어야 한다(*)
			spec:
			  containers:
			  - name: php-redis		# 컨테이너이름
				image: us-docker.pkg.dev/google-samples/containers/gke/gb-frontend:v5		# Pod의 base 이미지명
		
		==> selector.matchLabels 값과 template.metadata.labels의 값은 반드시 같아야 한다 (***)
	
	--------------------------------------------------------------	
	# 실습1. replicaset 생성/조회
	
	1) replicaset.yaml 작성

			apiVersion: apps/v1
			kind: ReplicaSet
			metadata:
			  name: rs-pod

			  # modify replicas according to your case
			  replicas: 3
			  selector:
				matchLabels:
				  app: web
			  template:
				metadata:
				  labels:
					app: web
				spec:
				  containers:
					- name: nginx-container
					  image: nginx:1.14.2
					  
	2)	생성

		rs-pod-gqrd9   1/1     Running   0          12s
		rs-pod-mtkgh   1/1     Running   0          12s
		
		==> NAME값은 ReplicaSet의 이름(rs-pod)를 prefix로 사용한다
		
	3) replicaset 조회 
	
		> kubectl get replicasets
		> kubectl get replicaset
		> kubectl get rs
		
	4) replicaset 상세 조회

		...

	1) 인위적으로 실행중이 pod 삭제

	https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/#isolating-pods-from-a-replicaset

			> kubectl get pods --show-labels

			rs-pod-mtkgh   1/1     Running   0          152m   app=web
			
		3) 모두 가제 
			> kubectl delete rs --all		# ReplicaSet을 삭제하면 관리하는 Pods도 삭제된다.
			> kubectl delete rs rs-pod --cascade=orphan

6장 K8s 주요객체3 - Deployments ( *** )
/////////////////////////////////////////
https://kubernetes.io/docs/concepts/workloads/controllers/deployment

1. 개념 : pod와 ReplicaSet 기능을 포함 및 추가 기능을 지원하는 리소스		

2. 추가기능
	- pod 자동복구
	- 버전관리 지원 ( tempplate를 수정해야 이력으로 남는다 => 관리되는 pod 쪽의 이력을 수정해야 된다 )
	- 롤백 ( 특정 버전으로 돌아갈 수 있다 )
	- scaling 가능 
	- 무중단 업데이트 가능 ( 롤링 업데이트: Rolling -update )
	https://discuss.kubernetes.io/t/rollingupdate-order-in-deployments-and-statefulsets/31998
	# 롤링 업데이트: Rolling -update
	# 기본 Pod를 일부분 삭제하고, 새로운 Pod를 일부분 생성하면서 전체를 새로운 Pod로 업데이트하는 방법
	# ==> 전체를 내리고 업데이트 하지 않으므로 서비스 중단이 없다

	
3. 기본 Deployment.yaml
	
	# sample
	apiVersion: apps/v1
	kind: Deployment
	metadata:
	  name: nginx-deployment	# Deploymet 이름
	  labels:					# Label 이름
		app: nginx
	spec:
	  replicas: 3
	  selector:
		matchLabels:
		  app: nginx			# ( ***** )
		  
	  template:					# Deployment 내의 ReplicaSet이 관리하는 Pod 정보
		metadata:			
		  labels:
			app: nginx			# ( ***** )
		spec:
		  containers:
		  - name: nginx
			image: nginx:1.14.2
			ports:
			- containerPort: 80

	==> selector.matchLabels 값과 template.metadata.labels의 값은 반드시 같아야 한다 ( **** )

4. Pod 교체 전략

	1) 개념
		- K8s의 Pod를 교체하는 방법이다
		
	2) 2가지 방버 
		
		가. 롤링 업데이트 방식
		https://discuss.kubernetes.io/t/rollingupdate-order-in-deployments-and-statefulsets/31998
			- 구버전 Pod를 삭제, 신버전 Pod를 생성하면서 업데이트하는 방식
			- 서비스 중단 없음
				단점: 배포 시간이 길어짐. 
					  버전들이 혼재함.
			
			# 샘플
			...
			replicas: 10
			...
			strategy:
			rollingUpdate:
			  maxSurge: 0
			  maxUnavailable: 2		==>	전체의 20v%를 삭제 할 수 있따
			type: RollingUpdate
			
			- maxSurge			: replicaset 보다 추가로 더 만들 수 있는 pod 비율
			- maxUnavailable	: 업데이트 중에 삭제할 수 있는 pod 비율
			
		-------------------------------------------------------------
		# yaml 파일	
			replicas: 10		
			maxSurge: 3
			maxUnavailable: 2		==>	전체의 20v%를 삭제 할 수 있따
			type: RollingUpdate
			
		# step1. 새로운 Pod 3개 생성 
			구버전: 10개 
			신버전: 3개 
			총	  : 13개 ( maxSurge )
		
		# step2. 구버전 2개 삭제 
			구버전: 8개 
			신버전: 3개 
			총	  : 11개 ( maxUnavailable )
			
		# step3. 새로운 Pod 2개 생성 
			구버전: 8개 
			신버전: 5개 
			총	  : 13개 ( maxSurge )
			
		# step4. 구버전 2개 삭제 
			구버전: 6개 
			신버전: 5개 
			총	  : 11개 ( maxUnavailable )
		
		# step5. 새로운 Pod 2개 생성 
			구버전: 6개 
			신버전: 7개 
			총	  : 13개 ( maxSurge )
			
		# step6. 구버전 2개 삭제 
			구버전: 4개 
			신버전: 7개 
			총	  : 11개 ( maxUnavailable )
		
		# step7. 새로운 Pod 2개 생성 
			구버전: 4개 
			신버전: 9개 
			총	  : 13개 ( maxSurge )
			
		# step8. 구버전 2개 삭제 
			구버전: 2개 
			신버전: 9개 
			총	  : 11개 ( maxUnavailable )	
		
		# step9. 새로운 Pod 1개 생성 	# replicas: 10 이므로 신버전은 10개를 넘어갈 필요가 없다.
			구버전: 2개 
			신버전: 10개 
			총	  : 12개 ( maxSurge )
			
		# step8. 구버전 2개 삭제 
			구버전: 0개 
			신버전: 10개 
			총	  : 10개 ( maxUnavailable )					
		-------------------------------------------------------------
		
		나. 재생성 방식
			- 개념: 구버전 pod를 모두 삭제하고 나중에 신버전 pod생성.
			- 장점: 배포시간이 짧음, 버전충돌이 없음
			  단점: 서비스 중단 발생( downtime 발생됨 )
		
5. Deployment 주요 명령어

		> kubectl get deployment		
		> kubectl get deploy
		
	3) Deployment 상세 보기

	4) rollout 명령어
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_rollout/
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_rollout/#see-also
	
		- 개념:
		- 문법: kubectl rollout SUBCOMMAND
		
		ex.
			# kubectl rollout history (TYPE NAME | TYPE/NAME) [flags]
			kubectl rollout history 	# 배포 이력 조회
			--revision=int	: revision 버전을 자세하게 확인 가능
			
			# kubectl rollout status (TYPE NAME | TYPE/NAME) [flags]
			kubectl rollout status 		# 배포 상태 조회			
			
			kubectl rollout restart		# 배포 재시작			
			kubectl rollout undo 		# 배포 롤백 ( 바로 이전 또는 특정 버전으로 롤백 )

			# 이전 버전으로 롤백 : kubectl rollout undo deployment/abc	
			# 특정 버전으로 롤백 : kubectl rollout undo daemonset/abc --to-revision=3
	
			kubectl rollout pause 		# 배포 일시중지			
			kubectl rollout resume		# 배포 다시 시작
