		# 전체적인 아키텍처 차이점
		
			가. SOAP 방식
								요청
				클라이언트 -----------------> 서버( Servlet, JSP, Thymeleaf )
			  (웹브라우저)	응답: HTML [ 하나의 페이지(view)를 응답 ]
			
			나. REST 방식
			
								요청: JSON/xml		(JAVA 베이스)
				클라이언트 <-----------------------------> 서버( @Controller + @RequestBody	<== 요청처리: JSON ---> JAVA
			  (웹브라우저	응답: HTML									 @Controller + @ResponseBody	<== 앙답처리: JAVA ---> JSON
				자동차,		[ 하나의 데이터(JSON)으로 응답		 @RestController = @Controller + @ResponseBody
				핸드폰,			따라서 화면이 필요하지 않다 ]
				... )
			
		# 클라이언트 요청 차이점
		
			가. SOAP 방식
				- GET: SELECT 할때, 멱등성 존재
						@GetMapping
				- POST: INSERT	( 멱등성 존재 안함 )
						, DELETE	( 멱등성 존재 )
						, UPDATE	( 멱등성 존재 )
						@PostMapping
			
			나. REST 방식
			
				- GET: SELECT 할때, 멱등성 존재
						 @GetMapping
				
				- POST: INSERT	( 멱등성 존재 안함 )					
						  @PostMapping
						  Content-Type:application.jon 필수 (매우 중요)
				
				- DELETE: DELETE	( 멱등성 존재 )
							 @DeleteMapping
				  
				- PUT: UPDATE	( 멱등성 존재 )
						 전체데이터 모두 수정.
						 @PutMapping
						 Content-Type:application.jon 필수 (매우 중요)
						 
				- PATCH: UPDATE	( 멱등성 존재 )	
							데이터 일부분만 수정
							@PatchMapping
							Content-Type:application.jon 필수 (매우 중요)
							
							
				==> 위와 같이 요청할 수 있는 도구가 필요함. ex. curl, postman, Talen API Tester(크롬 플러그인)
				
		# Controller 차이점
			
			가. SOAP 방식
				- 화면(View)이 존재하기 때문에 Controller에 View정보를 설정해야 된다.
				@Controller
				public class TestController{
					
					@GetMapping("/welCome")
					public string showPage(){ return "hello"; } // 뷰정보, hello.html
						
					@GetMapping("/json") ==> 뷰: json.html / 모델: LoginDTO
					@ResponseBody ==> /json을 뷰정보로 사용하지 않고, LoginDTO를 그대로 응답(JSON으로 응답)
					public LoginDTO showPage(){ return new LoginDTO("hong","1234); } 
				}
			
			나. REST 방식
			
			//	@Controller
				@RestController	//@Controller + @ResponseBody
				public class TestController{
					
					@GetMapping("/welCome")
			//		@ResponseBody
					public string showPage(){ return "hello"; } // 뷰정보, hello.html
						
					@GetMapping("/json") ==> 뷰: json.html / 모델: LoginDTO
			//		@ResponseBody ==> /json을 뷰정보로 사용하지 않고, LoginDTO를 그대로 응답(JSON으로 응답)
					public LoginDTO showPage(){ return new LoginDTO("hong","1234); } 
				}
				
		# 클라이언트에서 서버로 전달하는 파라미터 차이점
		
			가. SOAP 방식
				- 일반적으로 QueryString 방식으로 데이터를 전달함.
				- 문법: http://localhost:8080/요청매핑값?key=value&key=value&...
				
					ex. http://localhost:8080/todo?id=1000&description=...
				
				- @RquestParam 이용
				
				- queryString은 요청 URL에 포함이 안됨, 데이터가 url 창에 표현만 된다.
				 ==> URL: http://localhost:8080/todo 
				
			나. REST 방식
				- 일반적으로 queryString 방식 대신에 URL에 데이터를 포함하여 전달함. 
				==> ? 없이 / 로 데이터만 전달된다.
			
				- 문법: http://localhost:8080/요청매핑값/값1/값2/...

					 ex. http://localhost:8080/todo/1000/...
					
				- @PasthVaraible 이용
				
				- 전달값은 요청 URL에 포함 된다.
				==> http://localhost:8080/todo/값1/값2/... 
				
				ex.
					@GetMapping("/todo/{id}")
					@ResponseBody
					public String showPage(@PasthVaraible("id") int userid ){ 
						return "hello"; 
					}
					
					@GetMapping("/todo/{id}/{description}")
					@ResponseBody
					public String showPage(@PasthVaraible("id") int userid,
												  @PasthVaraible("description") String description){ 
						return "hello"; 
					}

	annotationProcessor 'org.projectlombok:lombok:1.18.34' 

- intellij에서 설정 추가
	
	settings >  Build, Execution, Deploy > Compiler > Annotation Processor > Enable Annotation procession
	
- 어노테이션 종류:

	@AllArgsConstructor	: 모든 변수를 포함한 생성자
	@NoArgsConstructor	: 기본 생성자
	@Getter					: getter 메서드
	@Setter					: setter 메서드
	@ToString				: ToString 메서드

2. ApiResponse 이용한 응답처리 개선	// 공통 응답객체	

	- lombok + @Builder 이용해서 생성
	- 사용자에게 더 많은 정보를 제공하자
	ex. 
		/*
		{
			 success: true|false,
			 message: "요청이 성공했습니다.",
			 data: {
				  "id":1,
				  "name":"홍길동",
				  "job": "Learn Spring"
			 }
		}
		 */
		@AllArgsConstructor
		@NoArgsConstructor
		@Getter
		@Setter
		@ToString
		@Builder
		public class ApiResponse<T> {

			 boolean success;
			 String message;
			 T data;

			 public static <T> ApiResponse<T> success(String message, T data){
				  return ApiResponse
							 .<T>builder()
							 .data(data)
							 .success(true)
							 .message(message)
							 .build();
			 }
			 public static <T> ApiResponse<T> fail(String message,T data){
				  return ApiResponse
							 .<T>builder()
							 .data(data)
							 .success(false)
							 .message(message)
							 .build();
			 }

		}

   @PostMapping("/todos")
   public ResponseEntity<ApiResponse<TodoDTO>> addTodo(@RequestBody TodoDTO todoDTO){
       int n = service.save(todoDTO);
       ApiResponse<TodoDTO> result = ApiResponse.ok("todo save success",todoDTO);
       URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                                                 .path("/{id}")
                                                 .buildAndExpand(todoDTO.getId())
                                                 .toUri();
       return ResponseEntity.created(location).body(result);
   }

4. 예외처리 ( 전역 예외처리 이용 )

	1) 사용자 예외클래스 생성
	
		- extends RuntimeException( ** , extends Exception이 아님 --> try catch를 하지 않기 위해서 )
		 
		ex. RecodeNotFoundException.java
		
		public class RecodNotFoundException extends RuntimeException{
			 public RecodNotFoundException(String message){
				  super(message);
			 }
		}
			
	
	2) 전역 예외 핸들러 작성
	
	ex. RestGlobalExceptionHandler.java
	
	@RestControllerAdvice
	public class RestGlobalExceptionHandler {

		 @ExceptionHandler(value = {RecodNotFoundException.class})
		 public ResponseEntity<ApiResponse<String>> RecodNotFoundException(Exception e) {
			  
			  ApiResponse<String> apiResponse = ApiResponse.fail(e.getMessage(),null);			  
			  System.out.println("RecodNotFoundException>>>>>>>>>>>>>>>>>>>>>>>>>>>>>");			  
			  return ResponseEntity.status(HttpStatus.NOT_FOUND).body(apiResponse);
		}
	}
