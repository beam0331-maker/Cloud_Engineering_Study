	5) Pod 내의 컨테이너에서 실행되는 어플리케이션( ex. SpringBoot) 로그 출력
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_logs/
	
		- 개념
		  : 컨테이너에서 실행되는 어플리케이션( ex. SpringBoot)의 정상로그(표준출력) 와 오류로그(표준에러)를 출력하는 명령어
		
		- 문법: kubectl logs [-f] [-p] (POD | TYPE/NAME) [-c CONTAINER]
		
			-f, --follow	: 인텔리제이 로그처럼 실시간으로 로그 출력 가능.
			-p, --previous	: If true, print the logs for the previous instance of the container in a pod if it exists.
			-c  CONTAINER	: 컨테이너명 지정			
			--tail n		: 마지막 로그중 n개 만큼 출력
			--timestamps	: 시간출력
			-p, --previous	: 만약 파드에 이전에 존재 했던 컨테이너가 있다면, 로그를 프린트해라
							  ex. CrashLoopBackOff 발생시 필수로 봐야된다
			-l, --selector string	: 필터링
			--since duration		: 지정된 시간 이후 로그만 출력 ( 단위 : 2s, 2m, 2h )
			
		ex.
			kubectl logs nginx-pod
			kubectl logs nginx-pod --tail 10
			kubectl logs nginx-pod --since=1m
			kubectl logs nginx-pod -c nginx-container
			
	==> 최종적으로 정리 
	
		kubectl get		: 상태확인용.
		kubectl describe: Events 확인용
		kubectl logs	: 사용하는 어플리케이션 (ex.  SpringBoot, Vuejs) 로그값 출력

	8) Label CRUD
		
		- 개념: label을 추가/수정/삭제/조회 하는 명령어
		- 문법: 
			kubectl label [--overwrite] (-f FILENAME | TYPE NAME) KEY_1=VAL_1 ... KEY_N=VAL_N [--resource-version=version]

		- 옵션
			--overwrite		: 기존 라벨 덮어쓰기 ( 수정 ) 
			--all			: 모든 리소스 선택
							  ex. kubectl label pods --all key=value	# 모든 pod에 라벨 지정
			-f FILENAME		: 지정된 파일의 리소스에 라벨 추가.
			--list			: 라벨 출력
			key-			: 라벨 삭제		ex. kubectl label pods pod4 app-  , env-
			
		ex.
			kubectl label pods nginx-container unhealthy=true		# 라벨추가
			kubectl label pods --all status=unhealthy				# 모든 pod에 라벨 추가
			kubectl label --overwrite pods nginx-container status=unhealthy		# 라벨수정
			kubectl label pods nginx-container bar-					# 라벨 삭제
			
			# 라벨 출력
			kubectl label pods nginx-container --list 	# 라벨 출력
			kubectl get pods --show-labels				# 라벨 출력
			kubectl get pods -L app,env					# 지정된 라벨을 column 으로 출력
			kubectl get pods -l app=nginx				# 지정된 라벨에 해당하는 pod 출력
			
			kubectl get pods -o yaml	
			kubectl get pods -o json

	11) 빠른 pod 생성
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_run/
	
		- 개념: 빠른 방법으로 pod를 생성하는 명령어
				실무에서는 yaml이용
		
		- 문법:
		kubectl run NAME --image=image [--env="key=value"] [--port=port] [--dry-run=server|client] [--overrides=inline-json] [--command] -- [COMMAND] [args...]
		
		- 옵션
			--image	: 컨테이너로 만들 base 이미지명
			--env	: 환경변수
			--port 	: 문서화 기능 			
			-it		: 표준입력, 모니터 활성화 
			--rm	: 종료시 삭자
			--dry-run	: 실제 생성하지 않고 YAML 확인가능
			--command 	: 명령어 지정
			-- 명령어	: 컨테이너에서 실생할 명령어 지정	
			--image-pull-policy	: ImagePullPolicy 지정( Always, IfNotPresent, Never)
			--restart	: restartPolicy 지정가능 (Always, OnFailure, Never)
			
		ex. 
			kubectl run nginx --image=nginx
			kubectl run nginx --image=nginx --dry-run=client -o yaml	# 실행되지 않고 yaml로 실행됨
			kubectl run nginx --image=nginx --restart=Never --port=79
			kubectl run nginx --image=nginx --env="DNS_DOMAIN=cluster"
			kubectl run -it pod9 nginx --image=nginx -- bash
			
			kubectl run pod9 nginx --image=nginx --rm

7장 Pod의 리소스 자원 (CPU/Memory) 관리
/////////////////////////////////////////
https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#requests-and-limits

1. 개념	: 여러 Pod들이 Node의 CPU와 Memory를 공유해서 사용한다. 
		  특정 Pod가 과도하게 자원을 점유하면 다른 Pod데 문제가 발생
		  ==> CPU, Memory 사용량에 대한 제한을 설정한다
	
	---------------------------
	Node ( PC )
	
	-----
	pod( SpringBoot )	- 희망 자원 : 최소한의 필요자원 지정 ( ex. CPU:1, Memory: 1Gi )
	-----				- 제한 자원 : 최대 사용할 수 있는 자원지정 ( ex. CPU:2, Memory: 3Gi )	  
									  CPU를 초과사용으로 사용제한 ( Throttling )
	-----							  Memory 초과사용으로 종료 ( OOMKill )		
	pod( MySql, Redis )
	-----
	
	CPU 자원 (ex. I7 12core)
	Memory 자원 (32g)
	---------------------------

2. 설정 방법

	spec:
	  containers:
		resources:
		  requests:		# 희망자원
			memory: "64Mi"
			cpu: "250m"
		  limits:		# 제한자원
			memory: "128Mi"
			cpu: "500m"
			
3. 단위

	가. CPU 단위	( MilliCPU )
		- 1000m = 1 CPU == 1 Core
		ex. 100m = 0.1 CPU
			250m = 0.25 CPU
			500m = 0.5 CPU
			1000m = 1 CPU
			
	나. Memory 단위
	
		- ki : kibi byte 	( 1ki = 1024 byte )
		- mi : mibi byte	( 1Mi = 1024^2 byte )
		- Gi : Gibi byte	( 1Gi = 1024^3 byte )
		
		ex. 1Gi = 1024MB
			128Mi = 128MB
			
4. requests
	- 개념 : 최소 보장 자원
			 ( 최소한 이 정도의 CPU와 Memory가 필요하다)
			 
	- 용도 : scheduler가 Pod를 어느 node에 올릴지 결정하는 기준이 된다.
			 중요한 것은 실행했을 때 필요한 자원이 기준이 아님. 
			  requests에 부합되지 않는 Node에는 배치되지 않는다.
			  
5. limits
	- 개념: 최대 사용 자원
	- 용도: 리소스(Pod) 보호.
			특정 Pod가 자원을 독접하지 못하도록 제한함.
			
	- 동작: 
		CPU가 초과되면 Throttling 발생 ( 최대 상한선에서 사용되도록 강제 )
		Memory가 초과 되면 강제종료 ( OOMKill 라고 부름 )
		
	
	# 실습1. CPU 실습
		
		1) yaml 작성( pod9.yaml )
			
			apiVersion: v1
			kind: Pod
			metadata:
			  name: stress-cpu
			spec:
			  restartPolicy: Never
			  containers:
				- name: stress
				  image: polinux/stress
				  args: ["stress", "--cpu", "1", "--timeout", "120s", "--verbose"]
				  # args: ["stress", "--vm", "1", "--vm-bytes", "300M", "--timeout", "120s", "--verbose"]
				  resources:
					requests:
					  cpu: "200m"
					  memory: "64Mi"
					limits:
					  cpu: "500m"
					  memory: "128Mi"
					  
		args: ["stress", "--cpu", "1", "--timeout", "120s", "--verbose"]
		==> CPU 1개를 이용해서 엄청낙 많은 연산작업을 수행함.

	# 실습2. Memory 실습
		
		1) yaml 작성( pod9.yaml )
			
			apiVersion: v1
			kind: Pod
			metadata:
			  name: stress-cpu
			spec:
			  restartPolicy: Never
			  containers:
				- name: stress
				  image: polinux/stress
				  # args: ["stress", "--cpu", "1", "--timeout", "120s", "--verbose"]
				  args: ["stress", "--vm", "1", "--vm-bytes", "300M", "--timeout", "120s", "--verbose"]
				  resources:
					requests:
					  cpu: "200m"
					  memory: "64Mi"
					limits:
					  cpu: "500m"
					  memory: "128Mi"
					  
		args: ["stress", "--vm", "1", "--vm-bytes", "300M", "--timeout", "120s", "--verbose"]
		==> Memory가 300M 필요하도록 스트레스 부하
			120초 이후에는 작업을 끝냄.

		2) Pod 생성 
			> kubectl apply -f pod9.yaml
			
		3) Pod 상태 확인		
			> kubectl get pods           
			NAME         READY   STATUS      RESTARTS   AGE
			stress-cpu   0/1     OOMKilled   0          13s
