3장 kubectl
/////////////////////////////////////////
1. 개요
	
	https://kubernetes.io/docs/reference/kubectl/
	- K8s 클러스터를 관리(제어)하는 명령어. (CLI 기반)
	- K8s 설치하면 자동으로 설치됨
	- Master Noded의 API Server와 통신
	
				kubectl get nodes
				(REST API 형태로 요청) 
		사용자 --------------------> API Server ----> 처리
		
2. 문법
	
	kubectl [command] [TYPE] [NAME] [flags]
	- command: 리소스(pod, service, ... )에 대해서 수행할 동작
			 ex. get		: 리소스 조회
				 delete		: 리소스 삭제
				 describe	: 상세 정보 조회
				 apply		: 리소스 생성/수정
				 logs		: 로그 확인
				 exec		: 컨테이너 접속/명령어 실행
				 rollout	: 배포관리 ( 롤백 포함 )	# rolling update가 기본이다
				 config 	: 클러스터 접속관리 ( 로컬 / 클라우드 )

	- TYPE: 대상이 되는 리소스 종류 ( 대소문자 구별안함, 단수/복수/약어 모두 가능 )
	# kubectl api-resources		# K8s이 지원하는 resource 목록확인
	
		ex. pod, pods, po 모두 가능
	
	- NAME: 리소스명 ( 대소문자 구별한다, NAME을 지정하지 않으면 모든 리소스 의미 )
		ex. kubectl get pods			# 모든 pod를 조회
			kubectl get pods my-pod		# 특정 pod(NAME)을 조회
			
	- flags: 옵션
		ex. -f		: 파일 지정.
			--all	: 모든것 의미 ex. kubectl delete all --all		# 모든 리소스의 모든 내용을 삭제
			-it		: 인터렉티브 접속.
			...

4장 kubeconfig 개요
/////////////////////////////////////////

	1) 개념
		- kubectl 클러스터에 접속하기 위해서 사용하는 설정파일
		- 윈도우: C:\Users\qja03\.kube\config 에 저장되어 있음. ( 나중에 AWS 클러스터 추가하면 이 파일에 추가됨 ) 
		- 리눅스: .kube/config
		
	2) 구성요소 3가지 
	
		가. cluster
			- 접속할 K8s의  클러스터 정보가 저장됨.
				ex. API Server 주소, 클러스터 이름
			
		나. contexts
			- cluster와 user 정보를 연결한 설정
			
		다. user
			- 접속할 사용자 정보.
				ex. 사용자명, 인증정보 등
				
	3) 특징
		- 여러 클러스터 정보 저장이 가능
		- 여러 사용자 정보 저장이 가능
		
		https://kubernetes.io/docs/reference/kubectl/generated/kubectl_config/
		
		kubectl - kubectl controls the Kubernetes cluster manager
		kubectl config current-context - Display the current-context
		kubectl config delete-cluster - Delete the specified cluster from the kubeconfig
		kubectl config delete-context - Delete the specified context from the kubeconfig
		kubectl config delete-user - Delete the specified user from the kubeconfig
		kubectl config get-clusters - Display clusters defined in the kubeconfig
		kubectl config get-contexts - Describe one or many contexts
		kubectl config get-users - Display users defined in the kubeconfig
		kubectl config rename-context - Rename a context from the kubeconfig file
		kubectl config set - Set an individual value in a kubeconfig file
		kubectl config set-cluster - Set a cluster entry in kubeconfig
		kubectl config set-context - Set a context entry in kubeconfig
		kubectl config set-credentials - Set a user entry in kubeconfig
		kubectl config unset - Unset an individual value in a kubeconfig file
		kubectl config use-context - Set the current-context in a kubeconfig file
		kubectl config view - Display merged kubeconfig settings or a specified kubeconfig file
		
		ex. 
			# 1. config 내용 조회
			config 파일 내용 조회
			kubectl config view			# 민감 정보 미출력
			kubectl config view --raw	# 민간 정보 출력
			
			# 2. 현재 사용중이 컨텍스트
			kubectl config current-context
			docker-desktop
			
			# 3. 현재 등록된 모든 컨텍스트 정보 조회
			kubectl config get-contexts
			CURRENT   NAME             CLUSTER          AUTHINFO         NAMESPACE
			*         docker-desktop   docker-desktop   docker-desktop

5장 K8s의 Configuration 설정 방법
/////////////////////////////////////////

	1) 개념
		- K8s에 리소스 (Pod, Service, ...)등을 어떻게 생성할 것인지를 정의하고 관리하는 방식관련 내용임.
	
	2) 방법 2가지 
		
		가. 명령형 구성 방법 ( Imperative Configuration ) 
			- 시스템에 직접 명령어 입력하는 방식
			ex. docker run -p 8080:80 nginx
				kubectl run nginx
				
			장점:
				즉각적으로 실행가능
				직관적임.
				
			단점:
				문서화 되지 않아 이력관리가 안됨.
				재현성 떨어짐				
		
		나. 선언형 구성 방법 ( Declarative Configuration )]
			- yaml 파일에 클러스터에 구축하고자 하는 원하는 상태(desired state)를 코드화 하는 방법
			
			- 장점:
				문서화 되어 있어서 이력관리가 가능하다
				재현성 향상
				대규모 운영에 유리
				
	3)  K8s의 YAML( Yet Another Markup Language, manifest 파일이라고도 부른다 )
		
		가. 개념
			- K8s의 클러스터가 원하는 상태( Desired state )를 갖도록 설정하는 파일(***********)
		
		나. 공통 구조
			
			apiVersion:	v1 | apps/v1	# API 버전, 확인방법: kubectl api-resources, kubectl api-versions
			kind: Pod | Deployment		# 생성하려는 리소스  종류 ex. Pod, Service, Deployment, ... 
										  대소문자 구별됨.
			metadata:					# Kind의 추가 설정정보.
										  ex. 이름, 라벨, 네임스페이스			
			spec:						# 리소스마다 다르다. 개별적인 리소스마다 정리 필요.
			
		다.	YAML 작성 가이드
			
			각 리소스마다 yaml 내용은 https://kubernetes.io/docs/home/ 검색해서 복사 / 붙여넣기 해서 사용한다.
			
			kubectl explain pod					# pod에 대한 소개 및 필드(field) 소개 
			kubectl explain pod.spec			# pod의 spec 소개
			kubectl explain.pod.spec.containers	# pod의 spec에서 containers 항목소개 
					
		라. kubectl과 yaml 처리 
		
			- 동작반식 
							pod.yaml --> JSON
				kubectl ---------------------------> API Server
			 (pod.yaml)

6장 K8s의 주요 객체 1 - Pod
/////////////////////////////////////////
	
1. 개념 
	- K8s 에서 관리( 생성/수정/삭제 )하는 최소 단위임 ( docker에서는 컨테이너가 최소 단위였음 )
	- Pod 안에서 하나 이상의 컨테이너를 포함함( 일반적으로 하나의 컨테이너를 가짐 ) 
	  # 하나의 Pod에 두개 이상의 컨테이너가있는 패턴 : 사이드카( Side car ) 패턴
	  
		https://kubernetes.io/docs/concepts/workloads/pods/

2. 특징
	1) Pod 안에 한 이상의 컨테이너를 포함함.
	2) Pod 안에 있는 컨테이너들이 네트워크와 볼륨을 공유할 수 있음 (****) 
	
	--------------------------
	Pod
	
		--------------
		container1
		--------------
		
		--------------
		container2
		--------------
		
		shared Network
		shared Volume
	--------------------------
	
	3) Pod는 일시적 ( Ephemeral ) 객체이다 ( 영구적인 객체가 아니다 )
		언제든지 제거될 수 있고, 새로운 Pod가 생성될 수 있다.
		ex. Node 장애 
			Pod 삭제 
			Deployment 업데이트
			Scale Out/In ( 트래픽에 따른 Pod 갯수 증가/감소 )
			
		==> Pod에서 처리한 데이터는 기본적으론 유지 불가( 영속성을 위해서 Volume 사용함 )
		  
	4) Pod는 직접 생성하기 보다는 다른 리소스를 이용해서 만드는것이 일반적이다.
		-> 더 많은 기능을 포함할 수 있기 때문
		ex. Deployment, StatefulSet, Job, CronJob
		
	5) Pod는 lifecycle 가짐.
		https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/
		
		pending --> runninng --> succeeded / failed
	
		pending		: Pod가 생성되었으나 아직 실행되지 않음
		running		: 하나 이상의 컨테이너가 실행중
		succeeded	: 하나 이상의 컨테이너가 모두 정상종료
		failed		: 하나 이상의 컨테이너가 비정상종료
		Unknown		: 노드와 통신불가로 인해 상태확인 불가
	
		확인방법: kubectl get pods
		
	6) RestartPolicy 정책
		- Pod가 제거된 후 재시작과 관련된 정책
		
		가. Always		: 컨테이너가 종료되면 항상 재시작된다.
		나. OnFailure	: 실패했을때만 재시작	# non-zero exit status: 0코드(정상종료코드)가 아닌 상태가 존재할때
		다. Never		: 재시작 하지 않음
		
	7) Image관련 정책 ( ImagePullPolicy )
	
		https://kubernetes.io/docs/concepts/containers/images/#image-pull-policy
		
		- Pod가 실행될때, 컨테이너에서 이미지를 언제, 어떤 방식으로 hub에서 가져올지 결정하는 정책
		- 정책 3가지 
			가. Always		: 매번 hub에서 가져온다
							  ( 로컬에 cached된 이미지가 있다면 로컬 이미지를, 없다면 허브에서 가져온다 )
				
			나. IfNotPresent: Node(local)에 이미지가 없을때만 다운로드 ( 가장 많이 사용 )
				
			라. Never		: 항상 로컬에 있는 이미지 사용
			
		- ImagePullPolicy를 생략했을 경우 기본값
			가. tag가 :latest인 경우
				- 기본적으로 Always로 동작됨
		
			나. tag가 특정 버전인 경우 ( :latest가 아닌 경우 )
				- 기본적으로 IfNotPresent로 동작한다
		
		
		- ImagePullBackOff
		https://kubernetes.io/docs/concepts/containers/images/#imagepullbackoff
			==> K8s가 이미지를 가져오지 못해 container를 생성하지 못하는 경우.
			
			원인 : 이미지 이름 오타, tag 오타, 로컬 이미지 없이 Never 지정한 경우
			
			==> kubectl describe pod <파드명>  확인 가능
	
	8) label 사용
	https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/
	
	- 개념: K8s 리소스( Pod, Service, Deployment 등 )에 설정하는 key-value 값.
	- 용도: 다른 리소스에서 접근할 때 label(ex. Pod) + selector(ex. Service) 사용함.
		
3. Pod 명령어

	1) Pod 생성 및 수정 
		
		- 개념: YAML 파일을 이용해서 리솟 생성/수정하는 명령어 
		- 문법: kubectl apply (-f FILENAME | -k DIRECTORY)
		
		- 특징:
			여러 번 실행해도 오류 안남 ( 없으면 생성하고 있으면 수정한다 )
			실행 중 수정 안됨.
			
		ex. 		
			# simple-pod.yaml		
			apiVersion: v1
			kind: Pod
			metadata:
			  name: nginx
			spec:
			  containers:
			  - name: nginx
				image: nginx:1.14.2
				ports:
				- containerPort: 80
			
			# yaml 파일 실행해서 pod 생성하기
			kubectl apply -f simple-pod.yaml
			kubectl get pods 	# pod 확이

	2) Pod 목록보기
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_get/
	
	- 개념: K8s의 리소스에 목록을 보는 명령어. 
	- 문법: 	
	kubectl get [(-o|--output=)json|yaml|kyaml|name|go-template|go-template-file|template|templatefile|jsonpath|jsonpath-as-json|jsonpath-file|custom-columns|custom-columns-file|wide]
	(TYPE[.VERSION][.GROUP] [NAME | -l label] | TYPE[.VERSION][.GROUP]/NAME ...) [flags]
	
	
	ex.

		kubectl get pods

		# List all pods in ps output format with more information (such as node name)
		kubectl get pods -o wide		
		
		# List all replication controllers and services together in ps output format
		kubectl get rc,services
		
		# List all deployments in namespace 'backend'
		kubectl get deployments.apps --namespace backend	# namespace로 만든 pod는 반드시 namespace를 설정해 줘야한다
		
		kubectl get pods --show-labels		# label 출력

	3) Pod 상세 보기 
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_describe/
	
		- 개념: 리소스 상세 정보를 출력하는 명령어 ( like. docker insepct )
		- 문법: kubectl describe (-f FILENAME | TYPE [NAME_PREFIX | -l label] | TYPE/NAME)
			
		ex. 
			# Describe all pods
			kubectl describe pods			# TYPE
			
			# Describe a pod
			kubectl describe pods/nginx		# TYPE/NAME
			
			# Describe pods by label name=myLabel
			kubectl describe pods -l name=myLabel	# TYPE -l label
			
		- 결과 창에서 살펴봐야 될 항목은 EVENT 항목

			가. pending	
				: CPU나 Memory 자원 부족인 경우제 주로 발생됨
			
			나. ImagePullBackOff
				: 컨테이너를 생성할 이미지가 없는 경우 .
				  ex. 이미지명 오타, tag 오타 
			
			다. CrashLoopBackOFF
				: 컨테이너가 계속 죽고 살아나는 동작을 반복
				  ex. 어플리케이션 오류, 환경변수 설정 오류, 포트 충돌
			
	-------------------------------------------------------------------
	
	4) Pod 삭제 
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_delete/
	
		- 개념: 리소스를 삭제하는 명령어
		- 문법: kubectl delete ([-f FILENAME] | [-k DIRECTORY] | TYPE [(NAME | -l label | --all)])
		
			--all		: 모든 리소스 삭제, ex. kubectl delete pods --all
			-f 파일명	: 파일안에 지정된 리소스를 삭제. 
			-l key-value: label 기반 삭제
			
		ex.
			kubectl delete pods 파드명
			
			# Delete a pod using the type and name specified filename
			kubectl delete -f filename		
			
			# Delete pods and services with same names "baz" and "foo"
			kubectl delete pod,service baz foo
			
			# Delete pods and services with label name=myLabel
			kubectl delete pods,services -l name=myLabel
			
			# Delete all pods
			kubectl delete pods --all

	# 실습1. Pod 생성 
	
		1) Pod 정의된 yaml 작성	( pod1.yaml ) 
		
			apiVersion: v1		# API 버전.
			kind: Pod			# 리소스 명, 확인: kubectl api-resources
			metadata:
			  name: pod1		# pod 이름
			spec:
			  containers:		
			  - name: nginx-container		# container 이름
				image: nginx:1.14.2			# 이미지 이름, 특정 버전을 지정했기 때문에 IfNotPresent로 설정된다.
				ports:
				- containerPort: 80			# port 포워딩
				
		2) Pod 생성			
			> kubectl apply -f pod1.yaml 
			pod/pod1 created
			
		3) Pod 조회 
			> kubectl get pods
			NAME   READY   STATUS    RESTARTS   AGE
			pod1   1/1     Running   0          65s
			
		3) Pod 상세 조회
			> kubectl describe pods/pod1
			
		4) Pod 삭제 
			> kubectl delete ( pods pod1  | -f pod1.yaml )
			pod "pod1" deleted from default namespace
			
			> kubectl get pods			
			# 이미지는 삭제 되지 않으니 docker rmi 로 삭제해야 한다.

	# 실습3. ImagePullPolicy 실습
	
		1) yaml 작성 ( pod3.yaml )
		
			# pod3.yaml
			
			apiVersion: v1
			kind: Pod
			metadata:
			  name: pod3
			spec:
			  containers:
				- name: nginx-container
				  image: nginx:1.14.2		# IfNotPresent 예상됨

				- name: redis-container
				  image: redis:latest		# Always 예상됨

				- name: busybox-container2
				  image: busybox
				  command: ["sh", "-c", 'echo "Hello, Kubernetes!" && sleep 3600']
				  imagePullPolicy: IfNotPresent		# latest는 Always가 기본값이지만 
													# Policy를 지정 해서 IfNotPresent가 나온다				  
		
		2) Pod 생성			
			> kubectl apply -f pod3.yaml 
			pod/pod3 created
			
		3) Pod 조회 
			> kubectl get pods/pod3      	
			
			> kubectl get pods -o yaml  	# imagePullPolicy 확인 가능
			
		3) Pod 상세 조회
			> kubectl describe pods/pod3
			
		4) Pod 삭제
